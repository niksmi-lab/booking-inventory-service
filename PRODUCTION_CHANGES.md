# Production hardening: что и почему изменено

Этот файл описывает изменения относительно исходного состояния проекта. Во время рефакторинга был создан локальный построчный diff, но он намеренно исключён из публичного репозитория, чтобы не сохранять старые конфигурационные значения и не создавать ложные срабатывания secret scanning.

## 1. Схема и миграции

**До:** `internal/storage/storage.go` выполнял один `CREATE TABLE IF NOT EXISTS` при каждом старте. SQL содержал лишние запятые после последних колонок, а код и индекс использовали отсутствующую колонку `expires_at`. Чистый запуск завершался ошибкой.

**После:** схема вынесена в `internal/storage/migrations/000001_init.sql`. Добавлены `expires_at`, timestamps, допустимые статусы, `CHECK` для количества, уникальность `(order_id, product_id)` и частичный индекс просроченных pending-резервов. `ApplyMigrations` фиксирует версии и использует PostgreSQL advisory lock.

**Почему:** схема должна быть воспроизводимой, версионированной и одинаковой у всех реплик.

## 2. Атомарность остатков

Файл: `internal/storage/inventory.go`.

**До:**

- restock отправлял batch без общей явно управляемой транзакции;
- повторяющийся товар в корзине ломал проверку количества обновлённых строк;
- reserve не имел ключа идемпотентности;
- cancel сначала возвращал остаток, затем удалял историю резерва;
- confirm подтверждал строки в любом состоянии и молча успешно обрабатывал неизвестный заказ;
- cleanup делал `UPDATE ... FROM expired` без группировки: для нескольких резервов одного товара PostgreSQL мог обновить строку остатка только по одному совпадению.

**После:**

- одинаковые позиции заранее объединяются;
- reserve блокирует товары `FOR UPDATE` в стабильном порядке;
- advisory lock по `order_id` сериализует один заказ между репликами;
- повтор идентичного reserve и повтор confirm/cancel идемпотентны;
- переходы состояния проверяются;
- истёкший резерв нельзя подтвердить;
- cancel/expiry сохраняют строки и меняют статус;
- возвраты группируются через `SUM(qty) GROUP BY product_id`;
- каждая DB-операция имеет timeout.

**Почему:** исключить oversell, двойное списание/возврат, потерю аудита и гонки между API и cleanup.

## 3. Домен и сервисный слой

Файлы: `internal/domain/inventory.go`, `internal/service/service.go`.

**До:** DTO/модель находилась в service package, ошибки были произвольными строками, `order_id` не проверялся, дубли не нормализовались, использовался глобальный текстовый `log`.

**После:** добавлены доменная модель и типизированные ошибки; лимиты 500 строк и 1 млрд единиц на товар; дубли суммируются с защитой от переполнения; элементы сортируются; используется внедрённый `slog.Logger`.

**Почему:** HTTP-слой может безопасно различать ошибки клиента, конфликты и внутренние сбои, а БД получает детерминированный набор позиций.

## 4. HTTP-контракт и безопасность

Файлы: `internal/handlers/handlers.go`, `internal/handlers/middleware.go`.

**До:** внутренний текст любой ошибки возвращался клиенту как 500; неизвестные JSON-поля и размер тела не контролировались; endpoints, включая restock, были публичными; отсутствовал request ID.

**После:**

- максимум тела — 64 KiB;
- разрешён только `application/json` и ровно один JSON-объект;
- неизвестные поля отклоняются;
- стабильный error envelope и корректные 400/401/404/409/500/504;
- тексты PostgreSQL не раскрываются;
- Bearer-аутентификация использует constant-time comparison;
- отдельные `API_KEY` и `ADMIN_API_KEY`;
- добавлены `X-Request-ID`, `nosniff` и `no-store`;
- metrics защищён admin-токеном;
- добавлен понятный `/cancel`, старый `/clear` сохранён как alias.

**Почему:** минимальная защита внутреннего API и предсказуемый контракт для других сервисов.

## 5. Конфигурация и lifecycle

Файлы: `internal/config/config.go`, `cmd/main.go`.

**До:** почти все параметры были зашиты в код; PORT из окружения игнорировался; пул БД не настраивался; сервер не имел `ReadHeaderTimeout`/`MaxHeaderBytes`; ошибка goroutine вызывала `os.Exit`; cleanup-worker не ожидался при shutdown; доверие proxy использовало defaults Gin.

**После:**

- централизованная fail-fast валидация env;
- ключи обязательны, различаются и имеют минимум 32 символа;
- параметры TTL, cleanup, shutdown и пула конфигурируются;
- настроены lifetime/idle/health-check пула;
- добавлены HTTP header/body timeouts и лимит заголовков;
- signal context, канал ошибки сервера и `WaitGroup` воркера;
- trusted proxies по умолчанию отключены;
- DSN не включается в ошибку парсинга.

**Почему:** управляемый запуск, безопасное завершение и отсутствие секретов в логах.

## 6. Наблюдаемость

Файл: `cmd/main.go`.

**До:** была только одна метрика количества запросов; лог не содержал request ID/размер ответа; path вычислялся до завершения middleware chain.

**После:** имена метрик имеют префикс сервиса, добавлена histogram длительности; логи содержат request ID, route template, status, bytes, duration и client IP; health и readiness разделены; readiness проверяет БД и обязательные таблицы.

**Почему:** запрос можно связать между ответом и логом, а latency и доступность БД — мониторить отдельно.

## 7. Контейнеры и секреты

Файлы: `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example`, `.gitignore`.

**До:** runtime использовал `alpine:latest` и root; builder копировал весь каталог, включая бинарник/секреты; compose содержал hardcoded-пароль, не ждал готовности БД и публиковал PostgreSQL на всех интерфейсах; env/gitignore имели ошибочные имена.

**После:** multi-stage build копирует только Go-исходники; runtime закреплён на Alpine 3.22 и работает как UID 10001; добавлены healthcheck, read-only filesystem, dropped capabilities и `no-new-privileges`; PostgreSQL опубликован только на `127.0.0.1`; секреты обязательны через `.env`; DB healthcheck участвует в `depends_on`.

Удалены заменённые файлы `f.env.example`, `g.env` и `s.gitignore`. Исходный собранный файл `main` не удалён автоматически, но теперь игнорируется Git и Docker build context.

## 8. Тесты

Добавлены:

- `internal/config/config_test.go` — env/defaults/fail-fast;
- `internal/service/service_test.go` — дубли, сортировка, validation и сохранение доменных ошибок;
- `internal/handlers/handlers_test.go` — error mapping, отсутствие утечки внутренних ошибок, strict JSON и auth;
- `internal/storage/inventory_integration_test.go` — реальный PostgreSQL, идемпотентность, concurrent oversell и агрегированный cleanup.

Фактически выполнены `go test ./...`, `go vet ./...`, PostgreSQL integration test, `docker-compose config -q` и `docker build`.

## Совместимость и дальнейшие шаги

- Теперь без `API_KEY` и `ADMIN_API_KEY` сервис намеренно не стартует.
- `/clear` продолжает работать, но новый код должен использовать `/cancel`.
- Начальная миграция предназначена для чистой БД; вручную исправленную старую схему нужно мигрировать отдельно после backup.
- Сервис готов к нескольким репликам на общей PostgreSQL, но rate limiting, TLS/mTLS/OIDC, backup и alert rules относятся к инфраструктурному слою.
